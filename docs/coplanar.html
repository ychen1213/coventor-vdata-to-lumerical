文件变小以后，CAD 为什么还可能很慢？

之前一份 AH53 的二进制 STL 有 2,463,058 个三角面，大小约 123.15 MB。STL 对每个三角形分别写三组坐标，相邻三角形虽然共用边，文件中仍然反复记录同一位置。因此把顶点集中放在一张表里、让三角形只记录顶点编号，可以先省下这些重复坐标。

但是，省掉重复坐标，没有省掉 CAD 需要处理的 246 万个面片。同一个大平面可能仍被切成许多细碎三角形。CAD 在建立实体、处理面与面连接、保存和重新打开时，仍需要处理这些面。

这就是为什么只把 STL 换成压缩 MAT，并不一定彻底解决导入慢。MAT 是一个数组容器：里面可以装三角面，也可以装多边形边界。只有进一步改变面片的表达，才能降低这一部分 CAD 工作量。

v0.4 的切入点：若许多相邻三角形本来就严格处于同一平面，将它们改记成一个具有相同外边界的多边形。已有的起伏、斜面和曲面不因“更平”或“更近”而被吸收到这个平面。

要判断这种操作有没有改变形状，先不要看复杂的 mark。下面只看一个平面矩形，逐项追踪面片、边界和顶点分别发生了什么。

同一片平面，可以用六个三角形，也可以用一个多边形记录

左边原来有六个三角形，围绕内部点 6 连接。合并以后，内部连接线无需再作为 CAD 面的分界；按顺序记录边界点 [0,1,2,3,4,5]，就能表达右边整块区域。

边界点 1 和 4 仍然保留。虽然删掉它们看起来还能画出一个矩形，但相邻曲面或其他平面可能也使用这些点和边。如果一边删掉、另一边保留，连接关系就可能失配。本程序保留合并片原来的全部边界顶点及边，只去掉平面内部的面片分界。

程序怎样确定“真的能合并”？

程序沿共享边寻找同向、连通的候选三角形，然后用现有浮点坐标的精确数值关系判断是否共面。这里的“严格”是零容差：没有“离平面不到 0.01 nm 就算平”的设置。浮点数本身是有限二进制数，可以转成精确整数比例来判定；它检查的是当前网格已经记录的坐标，不是推断物理界面是否平坦。

对通过共面检查的片区，再提取它的有向边界，并检查绕序、拓扑和区域一致性。单个闭合环可以是凹多边形。但如果一片平面有孔，它就有外轮廓与孔洞轮廓等多个环；本版在这种情况下保留原来的三角形，不冒险把孔洞填平。不能满足检查的片区也保留原划分或拒绝输出，不使用近似合并补救。

“删除未引用顶点”又多做了哪一步？

前面的合并只是改变面怎样引用点。教学例子的点 6 可能还留在总顶点表里，尽管没有面再用到它。开启 --compact-vertices 后，程序扫描最终面索引，只保留仍被引用的顶点，再更新编号。被使用的坐标不移动，也不舍入。边界上的共线点仍被引用，因此不会被这一步删掉。

这有别于 QEM：QEM 可以移动、折叠边并改变表面；这里既不将“差不多共面”当作共面，也不为了减少顶点改变边界。它同样有别于旧的 --planar-optimize：旧选项只对严格轴向、凸、单环平面进行重新三角化；新出口可以保留单环凹轮廓并直接向 CAD 交出多边形。

现在得到的是“坐标表＋若干长短不一的边界编号”。接下来要解决的只是怎样保存这些编号，以及怎样让 Lumerical 按同一顺序重新建立面。

MAT 保存边界编号，LSF 把这些编号交给 Lumerical

三角形固定使用三个点，可以放进每行三个数的表格。多边形可能用 4 个、6 个、数百个点，不能简单地要求每行一样长。用零填满到最长那一行，可能造成巨大的内存浪费。

本程序采用一种常见的紧凑记录方式，简称 CSR：把所有面的编号顺序接成一条长数组，再用另一条数组标出每个面的起止位置。这个名字也常用于稀疏矩阵；这里它只是一种保存变长列表的方法。

教学示例（Python 从 0 编号，仅演示变长列表）：
面 A 的边界：[0,1,2,3,4,5]   共 6 项
面 B 的边界：[2,3,4]         共 3 项

连续编号 indices：[0,1,2,3,4,5, 2,3,4]
边界位置 offsets：[0,6,9]

面 A = indices[0:6]
面 B = indices[6:9]

这两条数组和顶点坐标一起写入 material_NNNN_coplanar.mat。导出时会转换为 Lumerical 的从 1 开始的编号。真实文件还包含整体平移；顶点的局部坐标与平移均使用米，避免把微米数值直接当成米。

后缀都是 MAT，内部却不一定是同一种文件

这里还遇到一个与几何无关、却会直接阻止导入的兼容性问题：旧的 export-planar 用 SciPy 写 MATLAB v5 文件。本轮本机 Lumerical 2025 R2 的 matlabload 拒绝了测试中的 v5 文件，无论是否压缩；但同机通过 Lumerical 内置 matlabsave 保存的 HDF5 文件可以读取。仅仅让 Python 成功回读，不能证明 CAD 也会接收。

因此，新 export-coplanar 改用 MATLAB v7.3 格式，其内部基于 HDF5，由开源 hdf5storage 和 h5py 写出。无需 MATLAB 安装、MATLAB SDK 或 Coventor SDK。它仍使用 .mat 后缀，但文件内部的组织方式不同，不能把旧 v5 文件改个名字就当作 v7.3。

新版依赖已加入普通安装列表；更新代码后重新执行 python -m pip install -r requirements.txt。本轮已经实际执行新生成的 LSF，验证这份 AH53 的普通版与清理版都可以建立 CAD 实体、保存并重新打开；具体范围见本轮记录。其他输入与软件版本仍应执行相同的交接检查。

真实 MAT 变量内容
vdata_poly_verticesN×3 的局部米制顶点坐标
vdata_poly_flat按顺序连接的边界顶点编号，从 1 开始，double 保存整数
vdata_poly_offsets每个面在 flat 中的起始位置，从 1 开始；末尾是 length(flat)+1 的终止位置
vdata_poly_translation_m加到局部坐标上的整体位移，单位米
如果想在 Python 中直接看到新 MAT 的数组

使用与文件格式匹配的读取器。下面只读取数组，不调用任何商业程序：

import hdf5storage
import numpy as np

data = hdf5storage.loadmat("material_0002_coplanar.mat")
vertices = data["vdata_poly_vertices"]
flat = data["vdata_poly_flat"].ravel().astype(np.int64) - 1
offsets = data["vdata_poly_offsets"].ravel().astype(np.int64) - 1
first_loop = flat[offsets[0]:offsets[1]]
print("顶点表：", vertices.shape)
print("面片数：", len(offsets) - 1)
print("第一个面的 Python 顶点编号：", first_loop)

上面减 1 是把 Lumerical 的 1 基编号还原为 Python 的 0 基编号，不改变坐标。这里不要使用旧 SciPy MAT v5 的 scipy.io.loadmat 示例。

配套 import_lumerical_coplanar.lsf 先用 matlabload 读取数值数组，再按 offsets 把每一段编号取出来，构造 Lumerical 需要的嵌套 cell。每个面的第一层 cell 里放一条单环边界，边界编号使用行向量。最后调用 addplanarsolid(vertices, facets)，并设置材料、名称和整体位置。

逻辑示意；变量名、范围检查和材料设置以生成脚本为准：
matlabload(".../material_0002_coplanar.mat");
facets = cell(number_of_faces);
for (i=1:number_of_faces) {
  facets{i} = cell(1);
  facets{i}{1} = transpose(indices(first(i):last(i)));
}
addplanarsolid(vertices, facets);

这条路线不先生成 STL。它也不是把体素数组装进 MAT：MAT 里仍然是表面几何，只是面不再全部被限制为三角形。Planar Solid 的 cell 接口见 Ansys 官方命令说明。

不要为了查看面片而对整个大对象执行 get("facets")。已有版本的读取接口可能将变长面展开为按最长面填充的庞大数组。脚本通过构造函数交入 cell，验证时应优先读取顶点、位置、材料并检查截面；不能因为写入采用紧凑数组，就假定所有读取接口也保持同样紧凑。

理解了 MAT 和 LSF 的分工，实际操作只剩两个选择：对已有转换目录补这个出口，或者从 VDATA 开始一次完成两段工作。

先复用已有网格，再按需要从头转换

下面使用 PowerShell，并假设已按 README 在源码目录建立普通 Python 环境。转换本身不调用 Coventor SDK、安装程序、许可证服务或 Lumerical。只有最后手工执行生成脚本时，才需要本机 Lumerical。

$toolPython = ".\.venv\Scripts\python.exe"
$outputDir = ".\outputs\sample_compact"

已有本程序的转换目录时，直接补多边形出口

把 $outputDir 指向包含 conversion_manifest.json 和已记录网格的目录。命令会检查清单和网格哈希，读取已有网格，不再解压原始 VDATA、不重新推断表面：

& $toolPython run.py export-coplanar $outputDir --min-faces 2

--min-faces 2 表示至少两个合格三角形才考虑合成一个面，默认就是 2；它不是误差容差。先生成保留原顶点表的普通版，下一步再生成可以并排比较的顶点清理版。源 VMESH/NPZ/STL 不会因导出被替换。

若从一个基础的单实体 compact 目录接手，新增的交接文件是：

sample_compact/
  meshes/
    material_0002_coplanar.mat   顶点＋变长多边形边界＋平移
  import_lumerical_coplanar.lsf  为全部导出材料创建 CAD 对象
  coplanar_report.json           合并统计、检查和输出记录

  conversion_manifest.json      原有清单同步更新
  ...                           原始记录与三角网格继续保留

本例多 3 个文件，基础 6 文件目录会成为 9 文件。多材料时每个实体有自己的 MAT，脚本和报告共用；已经导出 STL 或其他 MAT 的目录，文件数会更多。以实际清单为准，不要把 9 当成任意输入的固定文件数。

接着生成清理版，比较相同表面的两套输出

& $toolPython run.py export-coplanar $outputDir `
  --min-faces 2 --compact-vertices

这次显式删除未引用顶点。新文件为 meshes/material_0002_coplanar_compact.mat、import_lumerical_coplanar_compact.lsf 和 coplanar_compact_report.json，普通版不被覆盖。刚才的单材料例子此时共 12 文件。若只执行清理版而未执行普通版，则从基础 6 文件变为 9 文件。

还没有转换目录时，从 VDATA 一次生成

& $toolPython examples/make_sample.py ".\outputs\sample.vdata"

& $toolPython run.py convert ".\outputs\sample.vdata" `
  --output ".\outputs\sample_coplanar" --storage compact `
  --coplanar --coplanar-min-faces 2 --compact-vertices

第一行仅生成演练用的人工 VDATA，不进行刻蚀工艺仿真。第二行先采用所选重建方法生成三角网格，再执行刚才的共面出口。实际数据换成自己的输入路径，新输出目录必须不存在或为空。是否先做旧平面重三角化、是否做 QEM，仍由各自参数决定；--coplanar 不隐含这些操作。

修正材料映射，然后在 Lumerical 执行正确的脚本

检查 material_map.json，名称必须与目标电脑的光学材料库完全一致。未知材料需要你指定，不可只看几何成功就默认材料也正确。例如：

{"materials": {"id:2": "Si (Silicon) - Palik"}}

更新材料映射或移动整个输出目录后，重新生成该路线的脚本和记录。沿用相同的合并与顶点选项，便于复现：

& $toolPython run.py export-coplanar $outputDir `
  --material-map "$outputDir\material_map.json" `
  --min-faces 2 --compact-vertices
  1. 打开 Lumerical FDTD 的空白工程。大型几何在已测试的 2025 R2 中使用 Classic 视口；其他版本先在小样上验证。
  2. 在脚本编辑器中打开并执行所选版本的脚本：普通版是 import_lumerical_coplanar.lsf，清理版是 import_lumerical_coplanar_compact.lsf。两个版本应在各自空白工程中比较，避免将同一几何叠加两遍。
  3. 检查对象数量、材料、坐标和几个侧面／水平截面；保存 FSP，重新打开，检查对象仍在正确位置。
  4. 几何交接完成后，才继续设置 FDTD 区域、光源、边界、网格和监视器。这里生成的文件和脚本不执行电磁求解。

操作完成后应先看报告确认“哪里少了面、哪里保留原面”。下面把这些数字能说明什么、不能说明什么说清楚，避免将 CAD 优化当成重建精度的提高。

怎样判断这次优化有效，以及它没有解决什么

coplanar_report.json 用于检查每种材料的输入三角面数、输出面片数、顶点保留／清理数量以及几何检查。面数下降小不一定是失败：曲面上没有严格共面的大片区域，或平面有多环孔洞时，安全回退本来就会保留更多三角形。

本轮正式程序已完成的验证：在本机 Lumerical 2025 R2 中，实际执行 v0.4 新生成的普通版与清理版 LSF，对复用已有完整 AH53 网格的两套输出均完成导入、保存 FSP、关闭／重新打开和坐标、材料、位置、旋转检查。另从原始完整 VDATA 实际完成一条 convert 命令，并将其输出与已通过 CAD 的来源逐字节核对。没有运行电磁求解。公开摘要见v0.4 验证记录。

从原始完整 VDATA 开始的一条命令，也已经实际走通

前表先复用已有网格，以便把 CAD 导入与顶点清理独立检查。随后又用同一真实 AH53 原始文件从头运行：

& $toolPython run.py convert `
  "D:\CoventorProjects\AH53_Si_300nm_Nonideal\AH53_Si_300nm_Nonideal.vdata" `
  --output ".\outputs\ah53_coplanar_compact_checked" --storage compact `

注意这里明确加了旧的 --planar-optimize。它先重新三角化合格的轴向凸平面，再由新 --coplanar 将合格片区表达成多边形；后者不隐含前者。运行自己的案例时，应选全新的输出目录，并根据需要选择这两项独立步骤。

这次解码、重建、旧平面优化和归档共 25.0873 秒，共面出口 78.4410 秒，阶段合计 103.5283 秒，不含 CAD 导入和电磁求解。生成 9 个文件，清理版 MAT 为 4,990,102 字节，原始 VDATA 的哈希不变。

独立检查确认：这次新 VMESH 的顶点、面索引及整体平移，与前面真实 CAD 验证所用的来源逐字节一致；新 MAT 的四个数组也全部逐字节一致。因此没有为了相同几何再重复运行一次 CAD。这样分别验证了“从 VDATA 到交接文件”和“正式 LSF 在 CAD 中接收并保存”的两段，并用数组一致性把两段连起来。

精度的参照始终是“已有重建表面”

共面合并的几何检查参照输入三角网格；顶点清理参照被实际使用的原坐标。它们不从 VDATA 恢复新的界面信息，不修复材料占比推断表面时的误差，也不能证明与未知的真实刻蚀界面一致。多材料仍沿用原来的独立重建结果；共面出口不自动建立共享界面、包含关系或 Mesh Order。

FSP 保存／重新读取可能有软件自身的浮点舍入；因此要把“输入数组坐标保持”和“商业软件往返数值检查”分开记录。检查界面与材料是否进入电磁求解器，还需要网格和光学验证。

本出口使用 MATLAB v7.3 / HDF5，实际可处理规模仍取决于可用内存、压缩和 CAD 对象开销；换一种容器并不是无限内存解决方案。输入必须是本转换器已经记录、闭合且绕序一致的材料表面；未知清单、损坏哈希、边非流形（共享边不恰为两面）或退化输入会被拒绝；本程序未检查全局顶点流形性。支持的 VDATA 编码范围也仍沿用读取器限制。

CAD 内存下降不等于 FDTD 求解器内存下降。前者与几何对象和面片管理有关；后者主要受计算区域、网格和场／材料数组影响。在相同求解区域和电磁网格下，不能将表中 CAD 的内存比例直接套到求解器。

这条升级的落点是明确的：复用同一张表面，减少 CAD 面片和无用途坐标，让文件交接与工程操作更轻。完成这一步后，再用一致的光学设置评价求解资源，才能知道后续真正的计算瓶颈在哪里。
